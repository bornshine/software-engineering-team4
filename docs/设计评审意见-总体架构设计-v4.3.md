## 一、总体结论

v4.3 把 v4.2 的详细设计压缩成 255 行的"总体架构蓝图"，完成了以下有价值的收口：

- 用 `PHASE_1~9` 与 `DEV_STAGE_1~5` 双轨命名解决了阶段编号冲突；
- 用 `.storage/sessions/<session_id>/session_state.json` + `events.jsonl` 收口了五库分裂；
- 把 `planner_master` 提升为编排器之外的共享决策服务；
- 明确 `cp_length_hours = max(EF)`，修正了 v3.0 `backend/cpm.py:148` 的"全部 `slack==0` 任务求和"问题；

但 v4.3 目前是"**架构总纲**"，不是可以独立支撑 M1"契约冻结"的详细设计；同时它对 v4.2 评审问题的闭环是**选择性**的，P0-7（`ConfirmationVoucher` 空清单绕过）等关键项没有在新文档中得到修订。以下 P0 项必须在 M1 编码前处理。

### P0-2 `ConfirmationVoucher` 仍然可被空清单/无 artifact 绑定绕过（v4.2 P0-7 未闭环）

- **位置**：文档属性第 9 行"零绕过 `ConfirmationVoucher`"；§2.1 第 110-111 行；M2 第 253 行；对照 v4.2 第 394-400 行的旧定义。
- **问题**：
  1. v4.3 只在多处写"必填 `ConfirmationVoucher`""零绕过"，但没有给出新 schema；
  2. 若沿用 v4.2 旧定义，`checklist_items: Dict[str, bool]` 仍没有 `required_checklist_keys`，空字典 `all({}.values())` 为 True 可绕过；
  3. 凭证没有绑定 `artifact_type / artifact_version / artifact_sha256`，同一凭证可复用于不同版本；
  4. `RequirementSpec.frozen` / `DesignSpecDocument.frozen` 没有 `model_validator` 强制"frozen=True ⇒ voucher 非空"；
  5. `GCheckItem` 没有 `mode: AUTO/HUMAN/HYBRID`、`checked_by`、`evidence`，G-5/G-6/G-7 的人工责任无法审计。
- **修改建议**：
  1. 在 `ideation_models.py` 中给出完整定义：
     ```python
     class ConfirmationVoucher(BaseModel):
         voucher_id: str
         gate_id: str                     # GATE_A / GATE_B / REQ_FREEZE / G-1..G-7
         artifact_type: str               # REQ / DS / PROP / DAG
         artifact_version: str
         artifact_sha256: str
         required_checklist_keys: List[str]
         checklist_items: Dict[str, bool]
         signed_by: str
         signed_at: str
         comment: str = ""
     ```

  2. `model_validator(mode="after")` 校验：`set(required_checklist_keys) ⊆ set(checklist_items)`；所有 required 键为 True；`artifact_sha256` 非空；`signed_by/signed_at` 非空；

  4. `GCheckItem` 补 `mode/checked_by/evidence`；
  5. 统一错误码 `ERR_VOUCHER_INCOMPLETE`（空清单、缺键、错哈希、无签名）。
- **验收检查**：空 `checklist_items`、缺一个键、错误 `artifact_sha256`、`frozen=True` 且 `voucher=None` 四种情况全部返回 400；合法凭证可提交并冻结；前端能显示"还缺哪几项"。

### P0-4 "单会话预算上限 16"与完整六轮 4 观点 Agent 协议自相矛盾

- **位置**：§3.1 第 140 行（"单会话预算上限 `16`、简化协议上限 `7`"）；§2.2 第 125 行（`UPSTREAM_MODE=llm`，`ReplyPipeline` P1 Schema 校验最多重写 2 次，计入 `LLMCallBudget`）；§2.1 第 107 行（`PHASE_2`：2 代码组件 + 4 观点 Agent，六轮完整/三轮简化）。
- **问题**：
  1. 若 `16` 指 LLM 调用次数（v4.2 的 `LLMCallBudget` 语义），完整六轮 × 4 观点 Agent = **24 次**，仅 `PHASE_2` 就超过 16；
  2. 还未计 `PHASE_3` 主策执笔、`PHASE_4` 三视角盲评（3 次）、`PHASE_7` PM Agent 拆解、`PHASE_8` QA/拍案，以及 Schema 重写最多 2 次的放大；
  3. 文档没有定义预算是"调用次数"还是"Token 数"，也没有按阶段拆分，`LLMCallBudget` 只在 `llm_client.py` 注释中出现；
  4. 默认 `UPSTREAM_MODE=llm` 下，`PHASE_2` 完整协议必然触发预算耗尽，M2 的"`PHASE_1~5` 端到端在 `llm` 模式可运行"无法成立。
- **修改建议**：
  1. 明确 `LLMCallBudget` 字段：`scope: session|phase`、`max_calls`、`used_calls`、`max_tokens`、`tier1_max_calls`、`reset_policy`；
  2. 给出按阶段默认值（示例，可按实际调整）：
     - `PHASE_1`：2 次；
     - `PHASE_2`：完整 24 次 + 4 次重写缓冲 = 28 次；简化 7 次；
     - `PHASE_3`：2 次；
     - `PHASE_4`：3 次；
     - `PHASE_7`：2 次；
     - `PHASE_8`：按任务数动态，另设 `EXEC_MODE` 预算；
     - 单会话总预算 ≥ 64 次（或明确按 Token 计）。
  3. 统一用 `ERR_LLM_BUDGET_EXCEEDED`；预算耗尽时是"降级 fixture/rule"还是"挂起人工"，必须二选一写清楚；
  4. 在 §2.2 增加"预算计算示例"：完整六轮 24 次的算术过程。
- **验收检查**：`UPSTREAM_MODE=llm` 下完整六轮协议能跑完且预算账本对得上；预算耗尽测试返回统一错误码；简化协议 7 次能跑完。

### P0-5 "单文件 SSOT + events.jsonl"双写没有事务/补偿定义，崩溃一致性只覆盖一半

- **位置**：§3.5 第 180-183 行；M1 第 252 行（"`session_state.json` 单文件崩溃一致性单测通过"）。
- **问题**：
  1. `session_state.json` 是唯一事务事实源，`events.jsonl` 是只追加审计流；两者是**两个文件、两个写入路径**，没有跨文件事务；
  2. 若先写 state 后写 event，event 可能丢失；若先写 event 后写 state，event 可能指向未提交状态；
  3. M1 的"崩溃一致性"只测 `session_state.json`，不测 `events.jsonl` 与 state 的一致性；
  4. `events.jsonl` 的 `seq` 没有与 `session_state.json` 的 `state_version`/`state_sha256` 绑定，回放无法判断"事件是否覆盖到当前 state"。
- **修改建议**：
  1. 定义写入协议：`prepare state → append event(seq, state_version, state_sha256, payload) → fsync events → atomic os.replace(state) → fsync dir`；启动时校验最后一条事件的 `state_sha256` 与当前 state 一致；
  2. 或采用 outbox：`session_state.json` 内维护 `pending_events`，写入成功后异步刷 `events.jsonl`，重启补发；
  3. `events.jsonl` 每条增加 `state_version`、`state_sha256`、`prev_event_hash`（可选哈希链）；
  4. M1 增加"三点 kill 测试"：写 state 前、写 event 后 state 前、state 写后 event 前，验证重启后无丢失/无悬空事件。
- **验收检查**：三种崩溃点重启后 `replay(events) == session_state`；`event_seq` 连续；无事件指向未提交版本。

### P0-6 S-4 路径白名单把 `.storage` 暴露给执行 Bot，违背"唯一事实源由存储层写入"

- **位置**：§3.6 S-4 第 197 行；§3.5 第 180-183 行。
- **问题**：
  1. S-4 允许写 `.storage/sessions/<session_id>/`，但该目录是 SSOT；执行 Bot 如果拥有该路径写权限，可绕过 `storage.py` 直接改写 `session_state.json`，破坏事务、审计与单写者；
  2. S-4 没有区分"谁在写"（storage 层 vs 执行 Bot），只按路径判断；
  3. 路径白名单中包含 `workspace/.../artifacts/`、`.storage/...`、`exports/...` 三类，但没有定义"Bot 只可写 artifacts"的角色约束。
- **修改建议**：
  1. 拆成两个 guard：`StorageWriteGuard`（仅 `storage.py` 可用，写 `.storage`）与 `ArtifactPathGuard`（Bot 只能写 `workspace/<session_id>/artifacts/` 和 `exports/<session_id>/`）；
  2. S-4 改为"按 principal/role 的路径白名单"：`role=BOT` → 仅 artifacts/exports；`role=STORAGE` → 仅 `.storage`；`role=EXPORT` → 仅 exports；
  3. `.storage` 对 Bot 只读，任何直接写返回 `ERR_SAFETY_GATE_VIOLATION`；
  4. 增加 `session_id` 正则校验（`^[A-Za-z0-9_-]{1,64}$`），拒绝 `../`、盘符和符号链接。
- **验收检查**：Bot 直接写 `.storage` 被拒；storage 层写 `.storage` 成功；Bot 写 artifacts/exports 成功；`../`/`C:\`/symlink 全部拒绝。

### P0-7 3D 零容忍黑名单的匹配规则未定义，v3.0 实测"3D 建模"（带空格）可绕过

- **位置**：§3.1 第 137 行（"2D/2.5D 能力标签白名单与 3D 零容忍黑名单（命中即抛）"）；§3.6 S-3 第 196 行；对照 v3.0 `backend/rules.py:227`。
- **问题**：
  1. v3.0 的 `check_3d_blacklist` 是 `text.lower()` 后对固定词条做子串匹配；黑名单词条是 `3d建模`、`3d骨骼蒙皮` 等**不含空格**的字符串；
  2. 实测 `"3D 建模"`（中间有空格）不会命中，`"三维建模"`、`"3DMAX"`、`"Blender"`、`"Maya"` 也不在词表；
  3. v4.3 只把黑名单外置到 `domain_packs/games_2d.json`，没有规定归一化、同义词、全角/半角与正则匹配规则；换一个写法即可绕过"零容忍"；

  5. `PHASE_1` 预检、`decomposer` 3D 复核、`S-3` 网关统一调用同一个 `check_3d_blacklist()`，禁止三处各写一套。
- **验收检查**：`3D建模`、`3D 建模`、`三维建模`、`3DMAX`、`Blender` 全部返回 `ERR_3D_PIPELINE_FORBIDDEN`；`2.5D 等轴测`、`伪 3D 序列帧` 不误杀；三个入口的测试结果一致。
