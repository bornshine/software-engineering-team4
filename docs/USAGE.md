# 使用文档 · 任务分解 Agent 系统

本文档说明：输入规格怎么写、角色卡怎么改、硬性记忆的结构与规则、
每条命令怎么用、多轮对话能说什么、产物是什么、常见问题怎么办。
所有命令都在**仓库根目录**运行，环境只需 Python 3（标准库，零依赖）。

---

## 1. 命令总览

| 命令 | 作用 |
|---|---|
| `python3 main.py decompose --spec <规格.json> --deadline <YYYY-MM-DD>` | 初始化：规格入库 + 分解出任务图 v1 + 生成 outputs 三件产物 |
| `python3 main.py chat` | 多轮对话：查看与修改任务图（提案—确认—落库） |
| `python3 main.py show` | 查看当前任务图概要与变更记录条数 |
| `bash tests/run_demo.sh` | 一键实测，输出写入 `outputs/demo_run.log` |

注意：`decompose` 是**初始化动作**——会把任务图库重置为 v1（规格库、约束清单、
变更记录是追加式的，不会被清掉）。日常改任务请用 `chat`，不要反复 decompose。

## 2. 输入规格格式（examples/spec.json）

规格是 JSON（不用 YAML，避免第三方依赖），结构如下：

```json
{
"项目": "多体讨论工作流系统",
"规格版本": "design-v1.0",
"模块": [
{
"id": "M1",
"名称": "讨论引擎",
"说明": "模块一句话说明",
"需求编号": ["REQ-001", "REQ-002"],
"depends_on": [],
"work_items": [
{
"key": "state-machine",
"标题": "实现讨论状态机与六轮协议推进",
"类型": "开发",
"能力": "状态机开发",
"工时": 24,
"验收方式": "自动",
"验收标准": "可独立判定的验收条件，写不出标准的工作项不要放进来"
}
]
}
]
}
```

字段说明：

- `depends_on`：模块级依赖（依赖哪些模块的接口），写模块 id；
- `work_items`：模块内的最小工作项，**一个工作项 = 一个任务**，不要把多件可独立
验收的事塞进一个工作项；
- `类型`：四种——`开发` / `测试` / `评审` / `人工`，决定依赖流水线顺序与可分配的角色卡；
- `能力`：所需能力标签，必须能在某张角色卡的「能力标签」里找到，否则分解报错；
- `工时`：预估工时（小时，整数）；
- `验收方式`：`自动` / `人工` / `混合`（沿用 v1.2 第 7 章的验收方式标注）；
- `验收标准`：**必填**，缺了校验不通过（任务必须可独立验收）。

### 依赖是怎么推导出来的（确定性规则）

- **同模块流水线**：人工 → 开发 → 测试 → 评审，后一类任务依赖同模块全部前一类任务
（例如测试任务依赖本模块全部开发任务）；
- **跨模块**：模块 A 依赖模块 B 时，A 的开发任务依赖 B 的开发任务（接口先就绪）；
B 没有开发任务时，依赖 B 的全部任务。

### 分配与限时是怎么算的

- **执行对象**：在角色卡中筛选「能力标签含所需能力、且负责该任务类型」的卡，
再在这些卡的承担者里选当前累计工时最小的一位（简单负载均衡）；
- **限制时间**：用 CPM 关键路径法——正推每个任务的最早开始/结束（小时），
项目总时长 = 关键路径长度；开始日由 `--deadline` 往前推（工作日口径，8 小时/日、
跳过周末）；反推最晚开始/结束，两者之差就是**缓冲**，关键路径任务缓冲为 0。
每个任务的限制时间包含：工时、开始日期、截止日期、缓冲小时、是否关键路径。

## 3. 角色卡（config/role_cards.json）

共 5 张，字段统一：角色名 / 角色类型 / 定位 / 承担者 / 职责 / 能力标签 /
负责任务类型 / 输入规范 / 输出规范 / 限制与禁止事项 / 限时与交付标准。

| 角色卡 | 承担者（示例） | 负责类型 |
|---|---|---|
| 任务分解Agent（规划者） | PlannerAgent | 规划 |
| 开发Agent | DevAgent-A、DevAgent-B | 开发 |
| 测试Agent | TestAgent | 测试 |
| 评审角色 | Reviewer | 评审 |
| 真人成员 | william、单禹杭、胡子昂、陈鲁喆 | 人工 |

**怎么改**：直接编辑 JSON——加人就往对应卡的「承担者」里加名字；某种活没人能干，
就给合适的卡补「能力标签」。改完对**新分解**生效；对话改派会即时按新卡复核。
注意：给一张卡加能力标签等于放宽它的承接范围，想清楚再加（比如把「测试」加进
开发Agent 的标签，就会破坏“评者/作者分离”那类约束的实际效果）。

## 4. 硬性记忆（memory/）

“硬性”的意思是：这些事实以结构化 JSON **原样存储、精确读取**，不靠模型记忆，
也不会被摘要改写；文件只能通过程序的写操作修改（原子替换写入），人不要手改。

| 文件 | 内容 | 规则 |
|---|---|---|
| `spec_library.json` | 设计规格库：原文 + 规格版本 + SHA-256 内容哈希 + 存入时间 | 相同哈希不重复存；哈希用来证明“规格没被悄悄改过” |
| `task_graphs.json` | 任务图库：每个版本的完整任务图 + 墓碑 + 编号计数器 | 每次落库变更生成新版本，旧版本保留可查 |
| `constraints.json` | 约束清单（C-01…） | decompose 初始化时写入默认硬约束，可按需在文件中追加来源明确的条目——请通过程序或提交记录说明来源，不要无痕改 |
| `changelog.json` | 变更记录：序号、时间、类型、说明、来源、版本前后 | 只追加，不删改；对话变更会注明“多轮对话（经用户确认）” |

两条铁律：

- **任务编号稳定不复用**：编号由计数器单调发放；任务被删时编号进「墓碑」
（记删除时间与原因），以后新任务也不会再用这个编号；
- **变更必留痕**：没有写进 changelog 的修改视为没发生。

## 5. 多轮对话（python3 main.py chat）

对话是**简单的多轮模型**：保留本次会话的历史与上下文——上一次提到的任务会被
记住，所以可以说「详情」指代它、在改派/改限时时省略编号。关掉会话上下文即清零，
但已落库的事实在硬性记忆里，不受影响。

### 能说的说法

| 说法 | 效果 |
|---|---|
| `列表` | 列出全部任务（编号、执行对象、工时、截止、关键路径标记） |
| `详情 T-02` / `详情` | 看任务全字段；无编号时指代上一次提到的任务 |
| `改派 T-01 给 DevAgent-B` | 生成改派提案；先按角色卡复核，不合规当场拒绝（如把开发任务派给测试Agent） |
| `改限时 T-03 工时 32` | 改工时并**按关键路径重算全部任务的限制时间**，提案里给出 diff |
| `改限时 T-03 截止 2026-12-20` | 人工调整单个任务的截止日期（留调整标记，不重排其余任务） |
| `接口变更 M3` | 先输出影响分析（本模块任务 + 沿依赖链的全部下游任务），再给出打「待复核」标记的提案 |
| `确认` | 落库当前提案：任务图版本 +1、写变更记录 |
| `取消` | 丢弃当前提案，不落库 |
| `变更记录` | 查看最近 10 条变更记录 |
| `帮助` / `退出` | 看可用说法 / 结束会话（未确认的提案不落库） |

执行对象可以写**承担者名**（如 `DevAgent-B`、`william`），也可以写**角色名**
（如 `测试Agent`，会落到该角色的第一位承担者）。

### 完整对话样例（节选自 outputs/demo_run.log）

```text
你：改派 T-01 给 DevAgent-B
Agent：改派 T-01 给 DevAgent-B（角色卡复核通过）
将产生以下变化（尚未落库）：
~ T-01 执行对象：DevAgent-A → DevAgent-B
输入「确认」落库（任务图版本 +1，写入变更记录），或「取消」放弃。
你：确认
Agent：已落库：任务图更新为 v2，变更记录已写入硬性记忆。变更：改派 T-01 给 DevAgent-B
你：接口变更 M3
Agent：模块 M3 接口变更：
本模块任务（需按新接口调整）：T-06、T-07、T-08
下游受影响任务（依赖链传递）：T-09、T-10、T-11、T-12
接口变更 M3：给 7 个任务打「待复核」标记
……
你：确认
Agent：已落库：任务图更新为 v3，变更记录已写入硬性记忆。
```

## 6. 输出产物（outputs/）

| 文件 | 说明 |
|---|---|
| `task_graph.json` | 任务图全量：概要（周期、总工时、关键路径）+ 每个任务的全部字段 |
| `tasks.md` | 人类可读任务清单表：编号/标题/来源模块与需求编号/执行对象/限制时间（工时+截止+缓冲）/依赖/验收 |
| `task_graph.html` | 静态可视化：SVG 依赖图（关键路径红线）+ 甘特条 + 任务表，零外部资源，浏览器直接打开 |
| `demo_run.log` | `tests/run_demo.sh` 的实测输出（分解 + 一轮对话变更 + 落库状态） |

注意：`task_graph.json / tasks.md / task_graph.html` 是 **decompose 时点**的快照；
对话落库后的最新任务图以硬性记忆 `memory/task_graphs.json` 的最新版本为准
（`python3 main.py show` 看概要）。这是有意的分工：outputs 是交付快照，
memory 是持续演进的事实源。

共享黑板、任务分解、执行编排、可视化界面），以 `--deadline 2026-12-25` 分解：

## 8. 常见问题

**Q：分解时报“找不到可承接的执行对象”？**
A：规格里某个工作项的「能力」没有角色卡能匹配。给合适的角色卡补能力标签，
或修正规格里的能力写法（必须与标签一字不差）。

**Q：报“循环依赖”或“悬空依赖”？**
A：检查模块 `depends_on` 是否互相依赖成环；任务层面的依赖由程序推导，
不会悬空，若报错多半是模块依赖写了不存在的模块 id 引发的连锁问题。

**Q：改限时（截止）之后，为什么别的任务截止没变？**
A：这是两种改法的区别——「改限时 T-xx 工时 N」会重排全图；「改限时 T-xx 截止 日期」
是人工点对点调整，只改这一条并留标记。要整体平移工期，请重新 decompose 并给新的
`--deadline`（会重置任务图为 v1，注意先确认没有需要保留的对话变更）。

**Q：对话里改派被拒绝怎么办？**
A：拒绝说明里会写清哪张角色卡、缺哪个能力标签。要么换一个合规的执行对象，
要么先改角色卡（见第 3 节）再改派——不要绕过程序直接改 memory 里的 JSON，
那会让任务图与变更记录对不上。

**Q：能不能接 LLM 让它自由拆分？**
A：当前版本刻意不接。按“流程确定性、内容概率性”的口径，拆分/分配/估时/校验
必须是可复现的确定性逻辑；将来若要让 LLM 提工作项草稿，也应只作为规格输入的
草稿来源，仍须走同一套校验才落库。代码里没有预留必经的 LLM 调用点，需要时在
`src/decomposer.py` 的 `build_raw_tasks` 之前加一层草稿生成即可，不影响其余模块。
