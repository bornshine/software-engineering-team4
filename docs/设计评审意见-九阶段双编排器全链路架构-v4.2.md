### P0-3 "五库 SSOT"实际是五个独立 JSON 文件，无跨文件事务

- **位置**：§6.4 第 339-353 行；C5 第 786 行；§9.3 第 745 行。
- **问题**：
  1. 文档称 `.hard_memory/` 为"唯一事实源（SSOT）"，但实际是 `ideation_sessions.json / spec_library.json / task_graphs.json / constraints.json / changelog.jsonl` 五个独立文件，**没有跨文件事务**。进程在两次 `os.replace()` 之间崩溃，会出现"任务图已写入、需求库没写入"的半状态；
  2. 没有执行运行态（任务状态、进度、Bot 负载）、主策记忆、主策拍案、观测数据的落盘位置；
  3. `changelog.jsonl` 没有事件 schema，无法 replay 重建状态；
  4. v3.0 现有 `memory/changelog.json` 是 `.json` 不是 `.jsonl`，与文档不一致；
  5. C5 的"重启进程后 `.hard_memory/` 无损恢复"目前没有可执行定义。
- **修改建议**：
  1. 改为**单文件** `session_state.json`（或 SQLite WAL 单库），保证一次事务提交；
  2. 若坚持 JSONL 事件溯源，定义 `events.jsonl` 事件 schema：`event_id / seq / type / payload / schema_version / occurred_at`，并提供 `replay_events()`；
  3. 明确 `task_graphs.json` 是否包含 `status/progress`；若不包含，新增 `execution_state.json`；
  4. 新增 `planner_memory.json`（PitfallMemoryItem）、`planner_verdicts.json`（PlannerVerdictRecord）、`observability.json`；
  5. 所有持久化文件加 `schema_version` 与 `migrate_session_state()`；
  6. 明确单进程假设（`threading.RLock` 只保证进程内），如支持多进程需文件锁或 SQLite。
- **验收检查**：模拟在任意两次写盘之间 `kill -9`，重启后状态与最后一次提交一致；任取一个 session 的五类数据同时恢复；`changelog.jsonl` 可 replay 出与 `session_state.json` 相同哈希。

### P0-5 `cp_total_hours` 定义错误，C8 的"严格等于"在一般 DAG 上不成立

- **位置**：§5.3 第 311 行；C8 第 789 行；对照 `backend/cpm.py:148`。
- **问题**：
  1. 文档公式 `CP_Progress = Σ_{t∈CP, SUCCEEDED}(duration+delay) / Σ_{t∈CP}(duration+delay)` 与代码 `cp_total_hours = sum(t.duration_hours + t.delay_hours for t in cp_tasks)` 都是"所有 `slack==0` 任务之和"，不是"关键路径长度"；
  2. 当 DAG 有**多条并行关键路径**时，`Σ(所有关键任务)` 会大于 `project_total = max(EF)`，C8 的"关键路径总工时严格等于 CPM 预计总工期"不成立；
  3. C8 的"严格小于全图累计工时"在纯链式项目（所有任务都在一条路径上）也不成立；
  4. 分母含 `delay`，关键任务延期后分母增大，CP 进度可能**回退**（例如从 28% 降到 26%），文档没有说明这是设计意图还是缺陷。
- **修改建议**：
  1. 明确四个量并全文统一：
     - `total_all_hours = Σ` 所有任务工期（全图累计）；
     - `cp_length_hours = max(EF)`（关键路径长度，等于 `project_total` 基线）；
     - `baseline_cp_length`（无延期基线）；
     - `project_total_hours`（含延期后的 `max(EF)`）；
  2. CP 进度分母使用**一条代表最长路径的** `cp_length_hours`，或定义 `critical_path_ids` 为单条链；不要对全部 `slack==0` 任务求和；
  3. C8 改为"单关键路径时 CP 长度 = 项目总工期；多关键路径时 CP 长度取最长路径；`cp_length ≤ total_all`，线性项目取等号"；
  4. 明确"延期导致进度回退"是否为预期：若是，在 UI 上加说明；若否，进度分母改用 `baseline_cp_length`，延期单独用 `delay_impact` 展示；
  5. 同步修 v3.0 `backend/cpm.py:148`，并加"双关键路径"单测。
- **验收检查**：构造两条并行 10h 关键路径 + 一条 5h 非关键任务的 DAG，旧公式和为 20h、`project_total` 为 10h；新 `cp_length_hours` 必须为 10h；C8 断言通过。

### P0-6 执行安全门 S-4 的路径白名单与 `.sandbox_git` 派生视图、导出包冲突

- **位置**：§5.3 S-4 第 317 行；§6.4 第 344 行；§9.3 第 746 行。
- **问题**：
  1. S-4 要求"所有交付物与 Git 工件路径必须严格落在 `.sandbox_git/` 与 `.hard_memory/`"；但 §6.4 同时把 `.sandbox_git/` 定义为"派生审计视图"（可重建）。把交付物写入可重建的派生目录，违背"`.hard_memory` 是唯一事实源"；
  2. `/api/export/bundle` 需要生成临时报告包，路径通常不在上述两个目录，会被 S-4 拦截；
  3. 没有区分"交付物"与"Git 工件"两类路径。
- **修改建议**：
  1. 新增 `workspace/<session_id>/artifacts/` 作为**交付物唯一根目录**；
  2. S-4 白名单改为：`workspace/<session_id>/artifacts/`、`.hard_memory/sessions/<session_id>/`、`exports/`；
  3. `.sandbox_git/` 只作为派生审计视图，不接收业务交付物；
  4. 导出包写入 `exports/<session_id>/`，作为显式例外并记录审计事件；
  5. 用 `Path.resolve()` + `is_relative_to()` 校验，拒绝 `../`、符号链接逃逸、Windows 盘符切换。
- **验收检查**：向 `artifacts/` 写文件通过；向 `.sandbox_git/` 写交付物被拒；导出包写入 `exports/` 通过；`../../etc/passwd` 被拒。

### P0-7 门禁凭证 `ConfirmationVoucher` 可被空清单/无 artifact 绑定绕过

- **位置**：§7.1 `ConfirmationVoucher` 第 394-400 行；`RequirementSpec` 第 532-543 行；`DesignSpecDocument` 第 571-582 行；`GCheckItem` 第 565-569 行。
- **问题**：
  1. `checklist_items: Dict[str, bool]` 没有必填键校验，**空字典 `all({}.values())` 为 True**，可绕过门禁；
  2. 凭证没有绑定"被确认的是哪个 artifact 的哪个版本/哈希"，同一凭证可被复用于不同版本；
  3. `RequirementSpec.frozen` / `DesignSpecDocument.frozen` 没有 Pydantic validator，可以 `frozen=True` 且 `voucher=None`；
  4. `GCheckItem` 只有 `passed/detail`，没有 `mode: AUTO/HUMAN/HYBRID` 与 `checked_by`，G-5/G-6/G-7 的人工/程序责任无法审计。
- **修改建议**：
  1. `ConfirmationVoucher` 增加：
     - `artifact_type: str`（`REQ` / `DS` / `PROP` / `DAG`）；
     - `artifact_version: str`；
     - `artifact_sha256: str`；
     - `required_checklist_keys: List[str]`（按 gate 配置）；
     - `checklist_items` 必须覆盖 `required_checklist_keys` 且全为 True；
  2. 用 `model_validator(mode="after")` 强制：
     - `frozen == True ⇒ voucher 非空`；
     - `RequirementSpec.frozen ⇒ 所有 RequirementItem.formal_check_passed`；
     - `DesignSpecDocument.frozen ⇒ g_checks 恰好 7 项且全部 passed`；
  3. `GCheckItem` 增加 `mode: Literal["AUTO","HUMAN","HYBRID"]`、`checked_by`、`evidence`；
  4. `ERR_VOUCHER_INCOMPLETE` 覆盖"空清单、缺键、签名空"三种情况。
- **验收检查**：空 `checklist_items` 提交返回 `ERR_VOUCHER_INCOMPLETE`；错误 `artifact_sha256` 被拒；`frozen=True` 但 `voucher=None` 在模型层直接报错。

### P0-8 P2"双编排器物理隔离"与 `planner_master` 跨段身份矛盾

- **位置**：§1.3 P2 第 42 行；§4.1 第 206 行。
- **问题**：P2 明确"两个编排器不共享运行态内存，唯一接口是冻结产物"；但 §4.1 把 `planner_master` 定义为"跨段按事件唤醒（阶段 1 预警、阶段 3 方案执笔、异常终裁、下游拍案门）"并"保持唯一跨段身份"。实现时只有两种选择：共享同一个 planner 实例（违反"不共享运行态内存"），或上下游各建一个实例（违反"唯一身份"）。文档没有给出第三种解释。
- **修改建议**：二选一并写清楚：
  - **方案 A（推荐）**：`planner_master` 是"外部共享服务/单例 Agent"，两个编排器只通过只读 `PitfallMemory` + 冻结产物调用它，不持有其运行态；架构图上把 planner 画在两个 subgraph 之外，用"service"标注；
  - **方案 B**：上游/下游各一个 planner 实例，但共享同一个 `PitfallMemoryStore`（只读/受控写），明确"实例不同、记忆同源"；
  - 在 §4.1 增加"实例 vs 服务"小节，说明哪些状态属于编排器、哪些属于 planner 服务。
- **验收检查**：架构图与文字一致；测试"关闭 planner 记忆后其他 Bot 无法读取"；测试"两个编排器重启后 planner 记忆仍一致"。
