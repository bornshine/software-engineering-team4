## 0. 一句话目标

做一套**面向 2D / 2.5D 游戏项目的项目管理任务可视化工具**：
把一份项目计划书拆成可管理的项目 task，把每个 task 明确分配到对应的 bot（Agent）身上，
并用图表把「多个 agent 如何联合推进、何时收拢到一处集中产出、何时再次散开分头干活」的过程看清楚；
同时知道**每一关（每个阶段/关卡）里每个 agent 各自走到了哪一步**。

---

## 1. 背景与现状（为什么要做）

- 本仓库 `D:\software-engineering` 当前实现的是《流程设计（作业2）》的后半段：
  设计规格 → 任务分解 → 任务图（DAG）→ 静态 DAG/甘特可视化。
  分解、分配、估时、校验已可跑通，但**产出是「一次分解的静态快照」**，
  没有回答「项目推进过程中，多个 bot 各自在做什么、走到哪、什么时候汇合」。
- 现状多 agent 体系**过于臃肿**：角色卡 5 张、角色类型 5 类、每类还带多个承担者实例，
  加上讨论侧常驻 agent，链路上的 LLM 角色数量与调用成本偏高，与「成本要压下来」的目标冲突。
- 现状角色/任务口径是**通用软件工程**口径（含大量与游戏无关的抽象层次），
  而目标项目方向已经收敛为 **2D 与 2.5D 游戏**：
  凡是围绕 3D 节点工作流（3D 场景/3D 节点/3D 资源管线）展开的环节、角色职责、任务类型，
  都是**不需要引入**的，应当从流程中剔除，而不是保留为「暂时不用」的死结构。
- 项目方（拍案人）明确指出：多 agent 流程中最关键的角色是**策划**，且策划需要**一锤定音的拍案机制**，
  并需要**一点点记忆**——但这份记忆只记录「踩过的坑／不能做什么」，**不得反过来限制策划的工作流**。

## 2. 需求总览（必须成立的六件事）

| 编号 | 需求 | 一句话验收口径 |
|---|---|---|
| R1 | 项目计划书 → 项目管理 task | 输入一份项目计划书，输出结构化、可管理的 task 清单（每个 task 粒度可独立验收） |
| R2 | task ↔ bot 的明确分配 | 每个 task 都能指认唯一负责的 bot；无人可接、重复违规都会被拒绝并给出原因 |
| R3 | 联合 / 集中 / 散开 的过程可视化 | 能用图表看出「分散并行 → 收拢联合 → 集中产出 → 再散开」的结构与时序 |
| R4 | 每一关 × 每个 agent 的进度可见 | 按阶段（关卡）切开后，能看到每个 agent 在该阶段的任务、完成度、阻塞与产出 |
| R5 | 多 agent 流瘦身 | 角色种类显著少于现状；每个角色可多实例；成本随角色种类下降而非随任务数线性爆炸 |
| R6 | 2D / 2.5D 导向 | 全链路不出现 3D 节点工作流相关环节；任务类型与能力标签面向 2D/2.5D 游戏制作 |

## 3. R1 · 项目计划书 → 项目管理 task

### 3.1 要的形态

- 输入：**项目计划书**（用户以自然语言/结构化文档给出即可，不限定单一格式），
  产出：**项目管理意义上的 task 列表**——不是代码工作项，而是「项目要推进的一件件事」。
- 每个 task 至少能让人/编排侧回答清楚：
  - 它要做的是什么（人话一句，能看懂）；
  - 它属于项目哪个阶段/关卡；
  - 谁来做（见 R2）；
  - 它什么时候必须完成；
  - 它做完之后算不算真的完成（可独立判定，不能只写「完成开发」这种不可判定的话）；
  - 它和别的 task 谁先谁后、有没有互相依赖。
- task 粒度要求：**一个 task = 一件能独立验收的事**。
  含多个独立验收点的必须拆；小到调度成本高于执行成本的应合并。
- 计划书中含糊、有歧义、机器无法裁定的地方，**不被默默脑补**——
  要么标为待澄清，要么升级给拍案人（见 R5 的拍案机制），不许由执行侧自行发挥后当作既定事实。

### 3.2 与现状的关系

- 沿用本仓库既有的**追溯与校验纪律**：task 必须能回溯到计划书的哪一条、每个 task 的验收方式被标注
  （自动 / 人工 / 混合）、缺执行对象或缺限制时间的 task 不许进入下游。
- 既有「依赖推导、CPM 限时反推、变更提案—确认—落库」等机制是**可复用的资产**，
  新能力应在它们之上生长，而不是另起炉灶重写一套。
- 计划书本身应当像既有设计规格一样**入库留痕**（版本 + 内容哈希 + 变更记录），
  避免「计划被悄悄改过、task 却还对不上」。

## 4. R2 · task ↔ bot 的分配

### 4.1 分配必须成立

- 每个 task 有且只有一个**负责 bot**；分配依据来自角色卡的能力与职责边界，
  不是随手指派，也不是按名字猜。
- 无人可承接时**报错并说明缺哪项能力**，由人决定是补角色卡还是改计划书；
  系统不得擅自放宽承接范围，也不得生成「待指派」task 混进图里。
- 分配要能被解释：「为什么是它」——类型对、能力对、当前负荷合理，三者都能当场答出。
- 运行期改派不是改个名字：目标 bot 要重新过一遍同样的资格复核，不合格当场拒绝并说明原因；
  改派要完整带上任务定义、已有中间产物与失败记录。

### 4.2 bot 的身份

- bot 是**具体的执行实体**，属于某个角色；同一个角色可以有多个 bot 实例。
- 一个 bot 同时只能推进它自己名下的 task；同一 bot 的多个 task 默认串行（除非明确允许并行）。
- bot 的能力边界由角色卡声明；**卡上没有的能力视为不存在**。

## 5. R3 · 联合 / 集中 / 散开 的过程可视化（核心图形诉求）

### 5.1 要表达的概念

项目推进时，多个 bot 的协作形态不是恒定的，而是**分阶段变化**的：

- **散开（并行分头）**：多个 bot 同时各干各的，互不阻塞；
- **联合（协同合流）**：若干 bot 的产出需要在同一处对齐/互为输入；
- **集中（收口产出）**：某个阶段的关键产出由少数 bot 汇聚完成，是项目前进的关键点；
- 随后再**散开**进入下一轮。

工具必须让这三态在**结构上**和**时间上**都看得见，而不是只给一张静态依赖图。

### 5.2 图形层面的要求

- 需要一种能同时表达「谁和谁在一起干活」与「什么时候聚在一起」的图：
  能体现 bot 之间的**编组/合流关系**，以及这些编组**随阶段的生灭与更替**。
- 需要能表达**阶段切面**：以关卡（阶段）为横轴，看出每个阶段上 bot 的分布是散是聚。
- 图表必须**诚实**：
  - 关键路径/关键合流点要能被识别出来（不能把一堆带缓冲的支线完成度刷成「快完成了」）；
  - 状态用**统一口径的着色**，同一状态在任何图里都是同一个颜色；
  - 没有数据就显示没有数据，不做「看起来完成了」的推测。
- 图形服务于**人做判断**：看到图就应该能立刻说出「现在卡在哪、谁在等谁、下一关谁最可能延期」。

### 5.3 交互（人不是看板上的旁观者）

- 图不只是只读展示：能从图上直接进入某个 task 的详情（交付物、验收标准、执行记录、变更历史）。
- 关键操作要可达且留痕：暂停/恢复、重试、改派、改限时、回滚到指定确认门。
- **等待人工时必须明确指出「在等谁的什么决定」**；没有回复不等于同意。

## 6. R4 · 每一关 × 每个 agent 的进度

### 6.1 阶段（关卡）视角

- 项目必须能被切成**若干阶段/关卡**，每个阶段有自己的产出物与进入/退出条件。
- 阶段是「联合—集中—散开」的容器：每阶段内部要能看出该阶段的散开/联合/集中结构。

### 6.2 agent 进度视角

- 在任一阶段上，能看到**每个 bot 的**：本阶段分到的 task 清单、已完成/进行中/未开始/阻塞的分布、
  已产出的交付物、遇到的异常与阻塞原因。
- 进度口径要防自欺：
  - 主口径为**关键路径完成工时 / 关键路径总工时**（不骗人但可能不好看）；
  - 辅口径为全图完成工时比；两者同时展示，不混用。
- 任一关键路径 task 延期，甘特/阶段图要**立刻**用其顺延量重算预计完成日并显著提示。

### 6.3 状态语义

- task 状态沿用既有状态机语义（未就绪/就绪/执行中/待验收/已完成/失败/阻塞/已跳过），
  跨三视图口径一致；
- 打回重做、重试耗尽、人工跳过等异常路径在图上必须**可见**，不能悄悄消失。

## 7. R5 · 多 agent 流改造：瘦身 + 拍案 + 记忆

### 7.1 瘦身（成本目标）

- **角色种类要合并**：现状的开发 / 测试 / 评审 / 人工四类执行角色必须收拢，
  目标是把角色种类压到**明显少于现状**（具体数字由承接 agent 论证，但每多一种角色都要有理由）。
  典型方向：验证与评审并入承接角色自身的交付纪律；领域确认与拍案合并为一个决策角色。
- **流程类职责用代码而非 LLM 承担**：凡「流程往哪走」的判断（阶段推进、依赖是否满足、
  能否启动、变更影响谁、限时怎么反推）由确定性逻辑负责，LLM 只负责「内容好不好」。
- 每个角色可有多个 bot 实例，**并发能力靠实例数调，不靠新增角色种类**。
- 合并角色时不得破坏两条底线：**作者与评价者分离的实质**、**验收标准不被降格迁就进度**。
  若某个底线因合并而失效，必须在文档中显式说明并给出替代机制。

### 7.2 策划：一锤定音的拍案机制（最重要）

- **策划是本体系里唯一必须配备的决策角色**，其他角色可以合并，策划不行。
- 策划享有**终局裁决权**：当出现分歧、僵局、打回超限、平局、或计划书本身存在机器无法裁定的歧义时，
  由策划**一次性拍板**，给出明确结论并落为可记录的产物。
- 拍案结论具有**强制力与终局性**：
  - 下游 task 不得对已拍案事项自行改写；
  - 若执行中发现拍案本身有问题，走**显式变更流程**（新版本 + 影响分析 + 留痕），而不是悄悄推翻。
- 策划享有**更高规格的模型配置**：在可用的模型档位中，策划应被分配到规格/能力最高的一档，
  其他角色按需降配。理由：策划的错误会污染全图，而不是局部返工。
- 策划的职责边界是**决策与拍板**，不是包办实现；策划不直接下场干所有活，
  否则角色省不下来、决策还会被实现细节绑架。
- 拍案必须**留痕**：谁拍、什么时候、拍的是哪一条、依据是什么、影响哪些下游 task，全部可回查。

### 7.3 策划的记忆（只有策划有，且只有这一种）

- 记忆中**只记录踩过的坑**：已经发生过的失败/错误/返工，以及由此得出的「不能再这么做」。
- 记忆的用途是**避免重复犯错**，不是**约束工作方式**：
  - 不得把记忆内容写成「必须按某流程做」「必须调用某工具」「不得考虑某方案」这类工作流限定；
  - 不得让记忆条目数量增长到限制策划的探索空间；
  - 记忆条目应当是**可解释的教训**（情境 → 错在哪 → 教训），而不是清一色的禁令清单。
- 其他角色**不需要**记忆系统；其余角色需要的只是「上一环节的产出」这类**产物传递**，
  不是长期记忆。
- 记忆必须**可查、可追溯、可修正**：能看出某条教训来自哪次实际事件，
  也能在教训过时后被撤销——否则坑会越积越旧，反过来变成新的限制。

### 7.4 2D / 2.5D 导向（明确不做 3D 节点工作流）

- 项目方向已转向 **2D / 2.5D 游戏**。整个多 agent 流的角色职责、task 类型、能力标签、
  阶段划分都应面向 2D / 2.5D 的制作实际。
- **不引入 3D 节点工作流**：不设 3D 场景/3D 节点/3D 资源管线相关的角色、任务类型、阶段环节，
  也不保留“将来也许做 3D”的占位结构——保留即成本。
- 2.5D 的含义需在设计规格中明确界定（视差、分层渲染、伪 3D 视角等），
  避免“2.5D”成为“3D 换个说法”的模糊地带。
- 现有角色卡/依赖规则/阶段划分中凡以 3D 前提写成的部分，应在改造中被**改写**而非仅加注释。

## 8. R6 · 2D / 2.5D 导向（承接面约束）

- 阶段划分应贴合游戏制作的实际推进形态（策划案 → 美术/资源 → 玩法逻辑 → 交互与界面 → 联调与验证 → 打磨），
  具体阶段名与数量由承接 agent 设计，但须满足：
  - 每阶段有明确产出物与可判定的退出条件；
  - 阶段之间体现「联合—集中—散开」的节奏，而非匀速平铺；
  - 阶段划分与 **R4 的进度视角**、**R5 的拍案点**、**R2 的 bot 分配**对齐，不产生两套并行口径。
- 任务类型与能力标签覆盖 2D/2.5D 制作所需的工作种类即可，不多设。

---

## 9. 明确不做什么（防止范围蔓延）

- 本轮**不做** 3D 相关的一切工作流与节点管理。
- 本轮**不做** 真实代码的自动生成与部署（执行由 bot 干，工具负责调度与呈现）。
- 本轮**不做** 多项目/多租户/组织级权限体系。
- 本轮**不做** 向策划的长期记忆灌入流程模板——记忆只装教训。
- 本轮**不做** LLM 自由发挥式拆分（内容由策划/受控角色产出，仍须过既有校验才入库）。

## 10. 完成判据（做完是什么样）

1. 丢一份项目计划书进去，能得到一份 task 清单：每条 task 有阶段、有负责 bot、有期限、
   有可判定的验收方式、能回溯到计划书原文。
2. 打开可视化，一眼能看出项目现在**散**在哪、**聚**在哪、**卡**在哪；
   能按阶段切面看到每个 bot 的进度，而不是一个笼统的百分比。
3. 任一 task 都能追问出「为什么分给他」「为什么是这个期限」。
4. 角色种类显著少于现状，能列出「每个角色为什么必须存在」的论证。
5. 策划角色在流程中有且仅有一个**拍案出口**，其裁决在流程里不可被绕过，
   且其模型配置高于其他角色。
6. 策划的记忆里查得到「哪次坑 → 什么教训」，且这些条目读起来**不像工作流禁令**；
   其他角色查不到记忆。
7. 全链路任何角色的职责、任何 task 的类型，都不会指向 3D 节点工作流。

## 11. 待拍案人明确的开放点（承接 agent 可自行决断的不在此列）

以下三点若拍案人有偏好，请指定；否则承接 agent 可按第 2 节的“明显更少”原则自行论证决定：

- 角色种类的目标上限数字；
- 阶段（关卡）的划分粒度；
- 策划的模型档位如何在当前可用的模型/供应商配置中落地（要求只有一条：高于其他角色）。

- **新增**：联合/集中/散开的图形表达、阶段切面与分 agent 进度视图、
